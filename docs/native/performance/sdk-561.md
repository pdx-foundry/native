# SDK-561: shared static discovery

Measured on 2026-09-21 on the Apple M4 and exact M45-observe installation described in
[SDK-559](../performance.md). The baseline includes the SDK-559 dependency settings and
SDK-560's one-hash-per-query change.

## Change and scope

`BoundAnalysis` now owns the immutable catalog used by public registry questions,
registry bindings, and fixture field setup. It computes named candidates once per
instance. The catalog retains candidates, symbols, and strings needed by repeated
field queries; it drops decoded fixups, scheduling code, and vtable data. No executable
buffer is retained in the catalog. Each public or binding read still loads and hashes
the executable before using the cached catalog. A detected change, missing file, or
path retarget permanently invalidates this `BoundAnalysis`.

The supervisor builds its own `Binding` from the installation. It does not accept the
caller's cached addresses. Content, fixtures, game state, and session observations are
not shared by this catalog.

## Release timings and memory

The [measurement driver](../../../tools/profiling/measure.py) built first and ran each
static executable twice. Its logs are in `.local/sdk-561-baseline/` and
`.local/sdk-561-after/`. Runs were sequential with ordinary filesystem caching; host
variation is visible in the first registry run. All commands exited zero.

| Workload | Before | After |
| --- | ---: | ---: |
| `registries` first | 1.76 s | 2.02 s |
| `registries` second | 1.51 s | 1.57 s |
| Loader parity first | 2.74 s | 1.98 s |
| Loader parity second | 2.52 s | 2.26 s |

The registry answer is unchanged; it has no second discovery to remove. Loader parity
does discovery in both analysis and bindings, so the cached catalog removes that repeat.
The first pair saved 0.76 seconds; the warmed pair saved 0.26 seconds. These timings are
observations, not a fixed latency guarantee.

An ignored M45 test exercises two public registry calls, two field questions from
different registries repeated once each, and two repeated binding requests on the same
`Native`. Under `/usr/bin/time -l` in release, it took 8.57 and 8.38 seconds before
the change and 4.48 and 4.39 seconds after. Peak resident set size was 439/432 MB
before and 422/420 MB after. A `ps` sample after the questions, while the test process
was held open, was 431 MB before and 412 MB after. RSS includes allocator-retained pages,
so this is a process-level bound rather than the catalog's exact heap size. The catalog
keeps only data used by its repeat callers.

The expanded ignored test also checks fixture field setup against the public field
answer. Temporary source-copy instrumentation for that expanded run recorded one
catalog build and one `binary::discovery::read` across ten verified executable reads,
six field-input reads, and two binding requests. The instrumentation and logs are in
`.local/sdk-561-instrumented-source/` and `.local/sdk-561-instrumented-fixture-phases/`.
Their wall times are not the uninstrumented benchmark.

## Verification

- `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`
- `STELLARIS_PATH=... cargo test --test static_questions -- --ignored` (4 passed)
- `STELLARIS_PATH=... cargo test --lib binding::analysis::tests -- --ignored` (3 passed)

The registry JSON and full field-answer JSON for `common/traditions` and
`common/tradition_categories` matched the pre-change outputs byte for byte, including
values, gaps, and reader identities. The parity tests cover registry names and fields.
The analysis tests cover repeated callers and changed/missing executable invalidation,
including bindings after restoration. A unit test keeps missing, duplicate, and
unavailable initial-loader errors. No game was started for these measurements.
